# Session

## User

打开 Obsidian 的开发者工具（Help → Toggle Developer Tools），看 Console 里超时错误的具体来源是 cortex 插件还是网络请求。

## Assistant

我无法直接打开你本地 Obsidian 的开发者工具——我没有图形界面访问权限。但你可以自己操作，我来告诉你看什么、怎么判断来源。

**操作步骤：**

1. **打开 DevTools**：`Help → Toggle Developer Tools`（或 `Ctrl+Shift+I`）

2. **切到 Console 标签**，筛选错误：
   - 点过滤器输入框，输入 `cortex` 或 `error`
   - 观察错误堆栈的前几行——如果来自 `cortex-chat`、`_cortex/`、`plugin:cortex`，那就是插件自身逻辑超时
   - 如果堆栈指向 `fetch`、`XMLHttpRequest`、`net::ERR_`，那是网络层超时（API 调用或远程请求）

3. **切到 Network 标签**，勾选 `Preserve log`，刷新 Obsidian 或触发一次 cortex 请求：
   - 看哪些请求耗时最长（点请求看 `Timing` 面板的 `Waterfall`）
   - 状态码为 `0` 且耗时很长的通常是 CORS 被拦截或服务端无响应
   - 观察请求目标域名——如果是 `localhost` 或本地 MCP 端口，是本地服务问题；如果是外部域名，是网络/API 问题

4. **切到 Performance 标签**（可选），做一次录制，看 CPU 时间花在哪——大量 `Evaluate Script` 可能说明插件在空共享记忆上做无效查询

**基于已有上下文的初步判断：**

上次会话中所有共享记忆（preferences / projects / people / decisions / recent）都是空的，每次请求都要做大量空查询和重试，这是最可能的超时根因。你可以先在 DevTools 里验证这个假设——如果看到大量对 `_cortex/memory/*.md` 的空内容读取请求，那就确认了。
